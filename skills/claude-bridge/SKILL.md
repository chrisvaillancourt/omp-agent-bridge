# Claude Code task bridge

1. Establish the task and working directory. Choose `work` when execution, edits, or temporary experiments can validate understanding, including during reviews; choose `read-only` only for deliberately static work. State deliverables, relevant paths, boundaries, repository instructions, and evidence in the prompt; specify an exact model ID and deadline only when needed. The tool's configured model and 600-second deadline are defaults. Generic calls do not resolve Git refs, capture a diff, or require a clean repository.
2. For an independent review, gather the actual base, diff, requirements, and pertinent context yourself; pass primary evidence through the prompt or readable workspace files, without substituting your conclusions. For implementation, say what Claude may change or exercise, including whether temporary files should be cleaned up. Call `claude_task` with `{prompt, mode, model?, timeoutSeconds?}`: `mode` is explicitly `"work"` or `"read-only"`; an optional `model` is an exact `claude-…` versioned ID, not an alias; `timeoutSeconds` is 1–1800.
3. Invocation starts the task without a bridge confirmation, including in non-interactive sessions. Use it within the user's task authorization; paid usage credits may be charged. OMP's host tool-access policy still applies. Work mode uses Claude's `auto` permissions with OS-user file/shell/network authority, without rollback or filesystem containment. Keep authentication inside the official CLI.
4. On success, inspect the actual workspace changes and verify delegated claims against the requirements. Assess review findings independently, including severity; an empty answer or no reported defect is not proof of correctness. Report `answer` and `limitations` with your verification and any remaining uncertainty. The bridge neither commits nor publishes automatically; do so only when requested or required by the containing repository's instructions.
5. On failure, report the code and prerequisite rather than treating partial output as completed work. Inspect remaining edits and address the failure before deciding whether another invocation is warranted; failed or cancelled runs can have changed files and consumed usage. The bridge does not automatically retry. When cost matters, compare Claude Code `/usage`, allowing for delayed reporting.

## Boundaries and recovery

The official unmodified CLI uses the signed-in user's own Team subscription, not an OMP model-provider credential. Paid credits can be charged; there is no included-allowance-only spending guarantee. Both modes disable ordinary customizations, MCP/Chrome/slash commands, and session persistence while trusting administrator policy. Read-only mode uses restricted mode, `dontAsk`, and Read/Grep/Glob with shell/edit/write/agent/task/web tools denied; its confinement is CLI policy, not an OS sandbox. Work mode uses `auto` with default built-in tools; actions requiring a permission prompt are denied rather than forwarded to OMP. Reported permission denials fail the task. OMP may retain inputs/results and Anthropic processes submitted content; no-session-persistence is not a zero-retention promise.

For installation, upgrades, profile selection, local state, stale-lock recovery, and failure codes, consult the [operator guide](../../README.md#installation-and-setup). Its `configure` and `check` commands are offline with respect to inference; `link` changes the OMP installation. Mutate configuration or link state only when authorized. A CLI upgrade merits compatibility investigation before re-pinning. The package, plugin, and local configuration use the `omp-agent-bridge` identity.
