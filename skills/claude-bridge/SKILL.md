# Claude Code task bridge

1. Establish the task and working directory. Choose `work` when execution, edits, or temporary experiments can validate understanding, including during reviews; choose `read-only` only for deliberately static work. State deliverables, relevant paths, boundaries, repository instructions, and evidence in the prompt; specify an exact model ID and deadline only when needed. The tool's configured model and 600-second deadline are defaults. Generic calls do not resolve Git refs, capture a diff, or require a clean repository.
2. For an independent review, gather the actual base, diff, requirements, and pertinent context yourself; pass primary evidence through the prompt or readable workspace files, without substituting your conclusions. For implementation, say what Claude may change or exercise, including whether temporary files should be cleaned up. Call `claude_task` with `{prompt, mode, model?, timeoutSeconds?}`: `mode` is explicitly `"work"` or `"read-only"`; an optional `model` is an exact `claude-…` versioned ID, not an alias; `timeoutSeconds` is 1–1800.
3. Present the bridge confirmation to the user. It authorizes this invocation only; a failure or later follow-up needs fresh interactive approval. Headless calls cannot proceed. Work mode has the OS user's file/shell/network authority, without rollback or filesystem containment; decide whether that authority is appropriate before approving. Do not replace the bridge with a shell/SDK/provider-token billing route.
4. On success, inspect the actual workspace changes and verify delegated claims against the requirements. Assess review findings independently, including severity; an empty answer or no reported defect is not proof of correctness. Report `answer` and `limitations` with your verification and any remaining uncertainty. The bridge neither commits nor publishes automatically; do so only when requested or required by the containing repository's instructions.
5. On failure, report the code and prerequisite rather than treating partial output as completed work. Inspect for remaining edits before retrying; a failed or cancelled run can have changed files and consumed usage. Another invocation requires its own approval. When paid credits are enabled, invite the user to compare Claude Code `/usage` before and after approved work.

## Boundaries and recovery

The official unmodified CLI uses the signed-in user's own Team subscription, not an OMP model-provider credential. Paid credits can still be charged. Both modes disable ordinary customizations, MCP/Chrome/slash commands, and session persistence while trusting administrator policy. Read-only mode uses restricted mode and Read/Grep/Glob with shell/edit/write/agent/task/web tools denied; its confinement is CLI policy, not an OS sandbox. Work mode permits arbitrary shell, filesystem, and network activity as the OS user. OMP may retain inputs/results and Anthropic processes submitted content; no-session-persistence is not a zero-retention promise.

For installation, upgrades, profile selection, local state, stale-lock recovery, and failure codes, consult the [operator guide](../../README.md#installation-and-setup). Its `configure` and `check` commands are offline with respect to inference; `link` changes the OMP installation. Mutate configuration or link state only when authorized. A CLI upgrade merits compatibility investigation before re-pinning. The local package/plugin/config identity still uses `omp-review-bridge`, despite the new public name and skill path.
